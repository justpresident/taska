# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Maintaining this file:** describe the current state, not the changes that produced it. No "X was renamed/moved/replaced", no "now"/"no longer", no closed-task references - a reader has no memory of the diff, so change-narrative is dead weight. Only forward-looking pointers to *open* work earn their place.

## What this is

`taska` is a local-first, git-native task & dependency tracker. The crate is `taska`; the binary is `ta`. Tasks live in an **append-only event log** (`.taska/mutations.jsonl`); the state you see is *replayed* from that log, never stored as a snapshot. A custom git merge driver reconciles concurrent edits on different branches per-field. See `README.md` for the user-facing model.

## Commands

```bash
cargo build                                          # build
cargo run -- <subcommand> [args]                     # run `ta` from source, e.g. cargo run -- list
cargo test --all --all-features                      # all tests (unit + e2e)
cargo test --lib                                     # unit tests only (in-crate #[cfg(test)] modules)
cargo test --test deps                               # one e2e theme (each tests/<theme>.rs is its own binary; helpers in tests/common/)
cargo test <name>                                    # a single test, e.g. cargo test crud_search_and_ready_workflow
cargo clippy --all --all-features --all-targets -- -D warnings   # lint (CI fails on any warning; --all-targets also lints #[cfg(test)] code)
cargo fmt --all                                      # format; CI runs `cargo fmt --all -- --check`
cargo bench --bench perf                             # perf table (replay/compaction/merge); no-dep harness, harness=false
```

CI (`.github/workflows/ci.yml`) runs test + clippy + fmt-check, and a separate coverage job via `cargo-llvm-cov` (it streams the ~2000 e2e `.profraw` files through `llvm-profdata merge`, which tarpaulin's in-Rust merge OOM'd on).

**The pre-commit gate.** CI fails on any clippy warning or fmt diff, so before each commit run clippy (with `--all-targets`, as above), `cargo fmt --all`, and `cargo test --all --all-features`. `--all-targets` is the easy-to-miss part: a plain `cargo build`/`clippy` skips `#[cfg(test)]` code, so a test broken by a model/signature change stays hidden until you lint with it. Build commit messages with `git commit -F` (a heredoc-in-`$()` mangles newlines); one task per commit, and keep the suite green at every commit.

**Clippy is strict.** `lib.rs`/`main.rs` enable `clippy::pedantic`, `nursery`, and `cargo`, and deny `unwrap_used`, `panic`, and `dbg_macro` in non-test code - write accordingly. Test modules opt back in with `#![allow(clippy::unwrap_used)]`; `unwrap` is the conventional assertion style there.

**`pub` vs `pub(crate)`.** `clippy::redundant_pub_crate` is denied and shapes every new file: inside a **private** module (`cli/commands/*`, `test_support`) use plain `pub` - the private parent already caps visibility to the crate, so `pub(crate)` is rejected as redundant; inside a **public** module (`cli`, `format`) use `pub(crate)` for cross-module-but-internal items.

## Architecture

The whole program lives in the **library crate** (`src/lib.rs`); the `ta` binary (`src/main.rs`) is a thin wrapper around `cli::run()`. Modules are layered by dependency inversion - lower layers know nothing of higher ones:

- **`model.rs`** - pure data, no I/O. `MutationEvent` (one log record), `OpType` (`Create`/`Update`/`Append`/`Add`/`Remove`/`Delete`/`AddEdge`/`RemoveEdge`; the accumulating trio commutes on merge - `Append` is FROZEN as text accumulation, `Add`/`Remove` carry numeric +/- and set insert/remove with config-free shape-dispatched replay; the keyboard operators are just `=`/`+=`/`-=`, dispatched per declared kind at write time), and the materialized `TaskState` (which also carries the computed `create_time`/`update_time`/`close_time`). Also `verify_seq_order`, `cmp_json` (the shared value ordering for `--sort` and the canonical set form), `cell_value` (the single column->value projection - `id`/`deps`/custom - shared by `format` rendering, `list`/`tree` ordering, and `list` filtering), `task_cmp` (the `--sort`/tree-sibling comparator built on `cell_value`+`cmp_json`, `id` tiebreak, missing-last), and `is_done` (the shared "status equals done_status" predicate, used across `engine`/`graph` and the action layer).
- **`engine.rs`** - pure replay. `Engine::materialize_report` folds a mutation log over a baseline into the current task map **and** reports *orphaned* events (an `Update`/`Append`/`AddEdge`/`RemoveEdge`/`Delete` that applied to no task); `materialize_state` is a thin wrapper that discards the orphans. `retention_split` decides what compaction folds. No storage dependency, so it's trivially testable.
- **`storage.rs`** - the `EventStore` *trait* (what a store can do, including `config()`) and `FileStore` (fd-locked JSONL on disk). Everything above depends on the trait, so tests substitute an in-memory fake (`src/test_support.rs`'s `InMemoryStore`, shared by the command tests). **v1.0 format floor:** this binary reads only v1.0+ stores. `FileStore::detect_legacy_format` raw-scans the log/baseline for pre-1.0 markers (an `AddDep`/`RemoveDep` op, an untyped/`dep`/`type`-keyed edge, a top-level `depends_on` baseline field) and the cli's `refuse_if_legacy` rejects such a store - intentionally, since the read shims are gone - pointing at `ta repair --migrate` on the last 0.x. So a v1 edge ALWAYS carries explicit `target`+`rel`; replay/merge skip one that doesn't, and `migrate.rs` holds the v1.0+ migration framework - currently no passes (v1.0 is the floor), `MIGRATIONS` is where new 1.x-era format passes go.
- **`graph.rs`** - dependency DAG over `petgraph`: cycle detection, topological sort, and `ready_tasks` (not-done tasks whose deps are all done). The graph is built from **blocker edges** (`graph::blocker_edges`): any relationship whose `kind` is `blocker`/`hierarchy` (per `RelationshipConfig::blocker_types`). All edges, `depends_on` included, live in `TaskState::relationships`; the `deps` column is that whole typed map (`{type: [targets...]}` in json, labeled type groups in human output - gating types bold, info plain). Informational (`info`) relationships never gate readiness/cycles/`dep tree`, and render plain (not dim): dim is reserved for a done/inactive task's whole row, so a dimmed info edge on an active task would misread as done. Callers pass the blocker-name set in, so `graph.rs` stays free of `config`.
- **`merge.rs`** - the git merge drivers (the most intricate module; see below).
- **`config.rs`** - `Config` and the `default_toml()` template `ta init` writes. The rendered template round-trips to `Config::default()` (a test enforces this).
- **`git.rs`** - registers the merge drivers in *local* git config and writes `.gitattributes` lines. Idempotent.
- **`format.rs`** - presentation: the `DisplayArgs`/`OutputFormat` flags, column resolution (`full_columns`, canonical order), per-column truncation, and the `human`/`json`/`jsonl` renderers. It renders an already-ordered slice - sorting lives in `model::task_cmp`, applied by the actions (`print_tasks` no longer sorts). `model::cell_value` is the single source of truth for "this column's value", shared by all three renderers (`deps` = the typed relationships map; the human renderers style its type groups via the blocker-type set threaded through `render_rows`/`print_tasks`). JSON/JSONL omit absent fields rather than emitting `null`. **Coloring is centralized in `RowStyle`** (built once per render from `[workflow]`): `paint_cell`/`cell_sgr` decide a cell's color - id cyan, the CONFIGURED status column green, a **done task's whole row/node grey (dim)**, deps by kind - and EVERY task renderer (table, record, AND `dep tree`'s `node_label`) styles through it, so all commands color identically and a new task-rendering command inherits it. Never reimplement row coloring in a command. **Output consistency contract:** `--format`/`--no-color` live in one `OutputArgs` struct that every output command flattens (tabular commands flatten it inside `DisplayArgs`; `status`/`dep tree`/`plan`/`cycles` take it directly). Tabular commands route through `render_rows`; structured commands build a human string (color-gated by `want_color`) + a `serde_json::Value` and pass both to the single `emit` dispatch (human / pretty-json / one-line-per-array-element jsonl). A new command that prints data MUST go through one of these - never hand-roll `println!` for structured output - and add itself to the `output_commands_are_format_and_color_consistent` e2e test, which enforces (json parses, never colored; human escape-free off-TTY).
- **`schema.rs`** - the **frontend-agnostic domain law**: the write gate (`vet_events` - no-op dropping, reserved names, whole-task `[task_types]` conformance with every violation in one error), the **soft-schema typo guard** (`vet_new_fields` - a write that introduces a field name outside the store's `known_field_names` vocabulary is rejected with a Damerau/OSA `osa_distance` did-you-mean unless `allow_new_fields`; `introduced_field_names` is the shared "what new names does this batch add" used by the guard and `edit`. The vocabulary = every field any task uses + declared `[task_types]` fields + `[display]` columns + status/type + reserved names. EMPTY-STORE GRACE: the first write on a task-less store seeds the vocabulary freely. Runs AFTER `vet_events` in `action::write`, so a closed type's own undeclared-field rejection wins where `--new-field` wouldn't help), schema-aware coercion (`coerce_event_fields`/`coerce_value`), the `+=`/`-=` accumulate dispatch (`build_field_events` over the frontend-neutral `FieldOps`), the default life-cycle (`schema_default_stamps`, `substitute_schema_defaults`), and `schema_conformance_report`. **Every frontend must funnel writes through `vet_events`** - and nothing in this module prints: reports return as data; `action::read` packages them as `Warning` data that the CLI's `print_warnings` (`cli/mod.rs`) renders to stderr. Both halves of the display<->canonical field-name boundary live here too: `canonical_field_pairs` (the shared list) and the **public** `canonicalize_fields` (display->canonical for writes - every frontend uses it, the cli is just one caller). Command logic itself lives in the frontend-agnostic `action/` layer (below).
- **`action/`** - the **frontend-agnostic action layer** (peer of `schema`/`engine`/`graph`): every operation a frontend performs, returning typed data + warnings-*as-data*, never printing. An action depends only on the `EventStore` trait + the domain layers - never on `cli`/`format`. `action::read` is the read pipeline (`Session { state, warnings }` - orphan/nonconformance detection, default substitution, timestamp injection, the canonical->display rename); the cli renders those `Warning`s via `print_warnings` (the one place that prints them). The display actions `list`/`show`/`status` return typed outcomes (`ListOutcome`/`ShowOutcome`/`StatusOutcome`, each carrying `warnings`) and own the *data* work (filter/criteria compilation, computed-column injection, inverse edges, count summary, and - for `list` - `--sort`/`--reverse` ordering, so it returns ordered data); the cli handlers shrink to render-the-outcome + print-warnings. The `dep` group is here too (`apply_edges` for add/remove; `cycles`/`plan`/`tree` reads) - `tree` returns a built-once `Node` forest whose nodes carry the caller's requested columns as `cells` (no field name hardcoded - the cli passes `display.columns` minus `id`/`deps`), and orders siblings/roots itself via the neutral `model::task_cmp` given the sort column. The writes share **`action::write`** - one verify-then-append choreography (`action::materialize` for raw state -> coerce/build -> `vet_events` -> `vet_new_fields` (the typo guard, gated by `allow_new_fields`) -> append, under the store lock) behind `write::create`/`update`/`delete`; `create`/`update`/`delete`/`edit` handlers all funnel through it. `create`/`update` return a `WriteOutcome` (the appended events + the new field names introduced, for the cli's redundant-`--new-field` warning); `create`/`update` take `--new-field`, while `edit` resolves the same new-field decision interactively (prompt: add vs re-edit) since it already has an editor loop. **Export convention:** only the four specific single-verb reads (`read`/`list_tasks`/`show`/`status`) are re-exported flat at `action::`; every multi-verb group - `write::`, `dep::`, `undo::`, `resolve::`, `config::`, `repair::`, `compact::`, `init::` - stays namespaced and is NOT re-exported (so there's no over-generic `action::plan`/`action::create`). The action speaks CANONICAL field names; a frontend maps display->canonical first via the **public** `schema::canonicalize_fields` (the cli is one caller, not the owner - see the canonical-field-keys note below). The interactive ones use **plan->apply** so `confirm` stays a frontend concern: `undo` (`undo::plan` previews the undone events + before/after and computes the resulting log; `undo::apply` writes it) and `resolve` (`resolve::plan` parses the merge marker + finds orphans; `resolve::apply` clears/prunes once confirmed) - both take a concrete `FileStore` (git inspection, marker file, `replace_mutations`). `compact::compact` returns a `CompactOutcome` the cli prints. `repair` (`migrate` + `schema`, returning `SchemaRepairReport`), `config` (`get`/`list`/`validate`/`set` - including the comment-preserving TOML edit), and `init` (the store/git bootstrap, returning an `InitOutcome`) round it out. **Every command drives through `action/`**; the cli handlers are thin parse-render shells. The action layer has zero `use crate::format`: the column->value projection and `--sort` comparator (`cell_value`/`task_cmp`) live in `model`, so both multi-result reads (`list`, `dep tree`) order their own data and the cli only passes a sort-column *name*.
- **`cli/`** - the CLI frontend. `cli/mod.rs` is clap parsing + `run()`/dispatch (the one global flag is `-C`/`--directory`: `run()` `set_current_dir`s into it before any discovery, git-`-C` style, so any command can target a store outside the cwd - e.g. a worktree driving the main checkout's `.taska` as a shared board. The clap-parsed value is authoritative for a real command; a completion callback exits inside `complete()` before that, so `run()` also applies `-C` from a raw-args scan when `COMPLETE` is set, so store-aware completions resolve against the `-C` store too) plus the cross-cutting helpers handlers share (`replay` for raw state, `parse_field_ops` - the `=`/`+=`/`-=` keyboard grammar that builds `schema::FieldOps` -, `confirm`, `print_warnings`); each subcommand handler is its own file under `cli/commands/`, and is a thin shell over the `action/` layer (parse args -> call action -> render) - the data work lives in `action/`, not here. Handlers take `&impl EventStore`, not `FileStore`. Beyond the README's commands there is `completions <shell>` (the clap_complete DYNAMIC registration shim printed to stdout - sourced into the shell rc, it calls `ta` back at completion time so task ids / filter fields / column names complete live from the store; the store-aware candidate providers live in `cli/complete.rs`, attached to args via `#[arg(add = ...)]`, with `CompleteEnv::with_factory(Cli::command).complete()` running first in `run()`; `--install [user|system]` instead writes the shim into the shell's auto-loaded completion file - sudo-fallback for a system path, a zsh-user `$fpath` edit - and `ta init` / `install.sh` set that up on a TTY, asking only user-vs-system, never whether (completions are non-destructive; skipped non-interactively); a no-store command like `init`), `self-update` (download this platform's latest GitHub-release binary via the `self_update` crate - ureq+rustls backend - and replace `current_exe` in place, then run the shadow-binary check; `--check` reports only, `--force` reinstalls, a platform with no prebuilt asset is pointed at `cargo install taska`. It touches neither the store nor the domain layers, so - unlike every other command - it lives entirely in `cli/` beside the shadow-warning machinery it reuses, NOT in `action/`; the release-asset contract it relies on - `ta-<tag>-<target>.tar.gz` containing `ta-<tag>-<target>/ta`, target = static musl on Linux / native on macOS, both arches each - is owned by `.github/workflows/release.yml`), `show` (one or more tasks - the deduplicated id list in first-occurrence order, an unknown id errors; human output is a vertical `field: value` record per task via `format::render_list_record`, untruncated - `--format json`/`jsonl` go the normal route), `status`, `config get/set/list/validate` (`validate` and `set` run `Config::validate_against(state)` - the cheap struct-only `Config::validate()` still runs on every other store command so a graph problem can't lock you out of the commands that fix it), `undo` (walk back through real history: `--seq`/`--count` select the original event(s), skipping prior compensations and already-undone seqs - see invariants), `edit`/`ed` (round-trip a task's fields through `$EDITOR` as TOML/`--json`; the saved file is diffed against what was shown - changed/added field set, deleted field unset via the null convention - and funnelled through the same `build_field_events`/`vet_events` write path as `update`, with a re-edit loop on any parse/canonical/schema error; relationships are out of scope, managed by `dep`), the `dep` group (`add`/`remove`/`tree`/`cycles`/`plan` - typed relationship edges validated against `[relationships]`, via `cmd_dep_group`/`DepAction`; there is no top-level `block`/`unblock`, and a task's relationships are surfaced by `show`, not a separate `dep list`), and `resolve` (which also prunes orphaned events). The display flag for "every field" is `--full` (not `--all`).
- **`error.rs`** - `DynError = Box<dyn Error>`; this is a print-and-exit CLI with no need for typed errors.

### Core invariants - do not break these

- **`seq` is the authoritative order, not the wall clock.** Each event carries a store-minted, strictly-increasing `seq`; replay, compaction, and merge all key off it. `timestamp` is informational (and used only as a *tiebreaker* by the `latest` merge strategy). The log must stay strictly increasing by `seq` - `verify_seq_order` *surfaces* a violation as corruption rather than silently sorting it.
- **`seq` is strictly increasing but need not be contiguous - gaps are allowed by design.** A `git revert` of a commit that added events removes those lines, leaving holes in the sequence; that is normal, not corruption (`verify_seq_order` rejects only out-of-order or duplicate seqs). Every seq computation is extremum-/position-based - `max(seq)+1` minting, `fork = max(ancestor seq)`, the `seq </> fork` filters, the renumber-to-contiguous tail in `assemble`, and the `min(seq)-1` watermark - so gaps reconcile correctly and the common revert (the reverted event still present in both logs) converges either merge direction. **Known limitation:** the merge's removal-detection (`removed_seqs`) only inspects ancestor events *above* a branch's `min(seq)-1` watermark, so a revert of a branch's *earliest* events - or one that compaction later folds past - is invisible and can resurrect the event or diverge by merge direction. The merge *warns* about the rewrites it **can** see - `rewritten_shared_seqs` flags a shared event present on one branch but reverted on the other, comparing only the region *above both* branches' watermarks (so ordinary compaction never trips it). The residual blind spot is a revert *below* the higher watermark (a branch's earliest events, or one compacted-past), which stays undetectable from the logs alone; documented in `protocol-doc`.
- **Writes are append-only.** `append_events` never rewrites existing lines (that is what keeps the log git-merge-friendly). `seq` is minted under an `fd_lock` write lock, as `max(seq)+1`, so concurrent writers can't collide. Only `compact` rewrites the log, and it holds the lock across the baseline swap.
- **Compaction never empties the log.** `retention_split` is clamped to always keep the last event, so the watermark `min(seq)-1` stays derivable.
- **`keep_events` has a floor** (`MIN_KEEP_EVENTS = 300`, see `config.rs`): retaining too few events would fold away history a concurrent branch still needs to merge. `Config::validate()` enforces it unconditionally on every store-backed command (there is no override; tests that exercise compaction stay above the floor and instead generate *more* events than `keep_events`).
- **`undo` walks back through real history and preserves the append-only invariant.** `undo` selects ORIGINAL events to reverse - newest-first, or from `--seq` (then `--count` older) - skipping events that are themselves compensations and originals already undone, so repeated `undo` peels back genuine history instead of bouncing on its own output. The "already undone" mark is `_meta.undoes=<original seq>` (`model::UNDOES_META_KEY`, read via `MutationEvent::undoes`/written via `set_undoes`): it rides INSIDE `_meta`, so it's never materialized into task state, drops on compaction, and needs no new reserved field name. **Compensations never replay specially** - they're ordinary events that already walk state back; the marker only drives `undo`'s own selection (and enables a future `redo`), so engine/merge/compaction are untouched (with `skip_serializing_if`, a non-undo event serializes byte-identically). Applying is hybrid: the clean uncommitted (or `--remove`) trailing run of selected events is truncated; committed or buried ones get *appended* compensations - one per original, tagged with its seq - that walk state to the target (always computed over the surviving ORIGINALS with compensations dropped, so old compensations can't pin/mask the removal; a shadowed event whose reversal is state-neutral still gets an inert marker so repeated `undo` makes progress). Naming an unknown/already-undone/compensation seq via `--seq` is a hard error. All of this lives in `action::undo` (`plan` computes the resulting log, `apply` writes it); `cli/commands/undo.rs` only renders the preview and runs the confirm.
- **Reserved keys & null-unset.** `seq`, `timestamp`, `op`, `task_id`, and `_meta` cannot be used as task field names (`RESERVED_FIELD_KEYS` in `model.rs`, which also reserves the built-in/computed columns - `id`, `deps`, `dep`, `unblocks`, `blocked_by`, `subtasks`, each a `model::*_KEY` const). `_meta` holds merge provenance and is deliberately *not* materialized into task state. A field written as JSON `null` is the **unset convention** - replay removes the field rather than storing null, so it never reaches state, output, list filtering, or the baseline.
- **Field-value input (`parse_field_ops`/`field_value`).** `key=value` sets a field, `key+=value` appends to it - `parse_field_ops` splits tokens into a *set* map (emitted as `Update`) and an *append* map (emitted as `Append`), so one `update` can do both (two events). Values coerce JSON-then-string; `key=@PATH` reads the value from a file and `key=@-` from stdin (verbatim string, one trailing newline trimmed - the agent-friendly way to pass long/multiline notes without argv quoting); `key=@@x` is the literal `@x`.
- **Orphaned events are non-fatal.** An event applying to a non-existent task is counted, never errored; replay continues. Commands warn when orphans are present, and `ta resolve` can prune them (dropping a no-op orphan can't change materialized state).

### The merge model

Merging two diverged logs is a **rebase**, not a CRDT union: keep our events, restack the other branch's concurrent events (those with `seq > fork`, where `fork = max(seq)` in the common ancestor) on top, renumber them into a fresh contiguous tail, and settle genuine contradictions with explicit appended **resolution events** that carry `_meta` provenance. Resolution is **per-field** - only a field/dep/whole-task that *both* branches changed incompatibly is a conflict; everything else merges untouched. **Removals are unioned**: an event present in the ancestor but dropped on a branch (a revert or hand-removal) is removed from the merge result regardless of which side dropped it, so a revert on either branch converges (`removed_seqs` in `merge.rs`). The `[merge] on_conflict` policy picks the winner for genuine conflicts: `surface` (default - writes a tentative ours-merge, flags it, and fails so git marks the path unmerged; reviewed via `ta resolve`), `latest`, `ours`, or `theirs`. The baseline has a separate keep-ours driver.

WARNING: The lowercase `serde` names of `Strategy`, `Side`, `TaskOutcome`, `EdgeOutcome`, and the `_meta`/conflict-marker field names are an **on-disk serialization contract** (search `merge.rs` for "SERIALIZATION CONTRACT"). Renaming a variant without a migration breaks existing logs.

### Computed timestamps work by read-time injection

`create_time`/`update_time`/`close_time` are computed onto `TaskState` during replay (so they survive compaction via the baseline), but they're surfaced by **injecting them as ordinary RFC 3339 string fields in `action::read`'s read pipeline**, under their configurable `[timestamps]` names. That read-time injection - not any per-feature plumbing - is why they "just work" as columns and in list filtering/`--sort`/`show`. Two consequences:

- `close_time` is the *most recent* close and is **cleared on reopen** (a deliberate product choice, not a bug).
- A test asserting an **exact** column/field set must disable timestamps for that store (`test_support::store_without_timestamps()`, or `[timestamps]` names set to `""`), or the injected times leak in.

The same injection pattern powers the computed graph columns `unblocks`/`blocked_by`/`subtasks` (transitive not-done dependents / prerequisites over the blocker edges from `graph::reachability_counts`, and direct-child completion from `graph::subtask_progress`), but **conditionally** and via one shared primitive: `action::inject_computed_columns(store, &mut state, wanted)` injects only the columns the caller names. `list` passes its displayed/sorted columns (`format::referenced_columns` -> `ListQuery::display_columns`) unioned with the filter-criterion fields; `dep tree` passes its configured columns (`display.columns` minus `id`/`deps`). So any **multi-result action is generically column-driven** - it returns exactly the columns asked for, with no hardcoded field names (so `dep tree` shows whatever columns it's given; the label field isn't special). That keeps default/`--full`/json output unchanged when nothing references them, so - unlike timestamps - they don't leak into exact-field-set tests.

The same boundary pattern gives the **canonical field keys**: events/baseline always store `status` (`model::STATUS_KEY`) and `task_type` (`model::TASK_TYPE_KEY`); `[workflow] status_field`/`type_field` are *display* names (defaults `status`/`type`) - `action::read` renames canonical->display on read, the **public** `schema::canonicalize_fields` maps display->canonical on write (rejecting a canonical spelling while a different display name is configured; the shared pair list is `schema::canonical_field_pairs`). Both halves of the boundary are in the domain layer, so EVERY frontend (not just the cli) can translate names - a write API that only the cli could feed canonical input to wouldn't be frontend-agnostic. Renaming either in config is therefore free - no data migration - and clones with different display configs merge cleanly. Mind the two state views: raw/engine state (vet, undo, merge, compaction) is always canonical, `action::read` state is display-named - pass the matching field name to `is_done`/graph helpers.

### Adding a config option: backfill the local config

`ta init` never overwrites an existing `config.toml`, so a new option is invisible in the dogfood store unless you **also add it (with its default + comment) to the repo's `.taska/config.toml`**, not just `default_toml()`. (TOML ordering bites too: scalar keys must precede any sub-table within a section.) Everything else is automatic - `Config` is `#[serde(default)]`, so partial/old files load and `ta config get/set/list` reflects the struct.

### Before adding a CLI command: prefer a flag, reuse what exists

A new subcommand is the last resort, not the first. Before adding one, work through this in order and record the reasoning (in the task notes / PR):

1. **Find the neighbours.** List the existing commands that do something similar (`ta list`, `ta show`, the `dep` group, ...). There is no `search` (it's `list --open`), no `ready` (it's `list --ready`), no `block`/`unblock` (it's the `dep` group) - a new capability usually belongs *next to* one of these.
2. **Default to a flag on an existing command.** If the new behavior is "the same view/data, filtered or ordered differently," it's a flag, not a verb - e.g. `list --ready` over a separate `ready`, `tree --plan`/`--all` over a new command. Only add a verb when the *output shape* or *primary noun* genuinely differs (e.g. `dep plan`'s flat dedup'd order vs `dep tree`'s nested structure - different output shapes warrant the split).
3. **If a flag, name it from the existing vocabulary** and make it compose with the flags already there (`--open`, `--full`, `--columns`, `--sort`, `--reverse`, `--format`). Don't invent a second way to express something a flag already covers.
4. **Generalize, don't fork.** Reuse the shared implementations rather than copy-pasting: an `action::*` for the operation itself, `model::cell_value` for any column's value (and `model::task_cmp` to order by one), `parse_field_ops` for `key=value`/`key+=value`, `graph::blocker_edges`/`validate_and_sort_dependencies` for traversal, `action::read` for the display-shaped map (`action::materialize` for raw), `confirm` for prompts. New data work belongs in `action`/`schema`; if two surfaces need the same logic, lift it into the shared helper (`action`/`schema`/`format`/`graph`) and call it from both - extend the primitive, don't grow a parallel one.

**Report before you build - mandatory.** Do not start implementing a command or a command-flag until the approach is confirmed. Surface the analysis first - the similar commands you found, whether it should be a flag or a verb, which flags make sense, and which shared primitives you'll reuse/generalize - propose the option(s), and get explicit confirmation. Implementation comes only after the user signs off.

The bar for a brand-new verb is: it can't be expressed as a flag, it doesn't duplicate an existing surface, and its core logic is built from the shared primitives above.

## Testing approach

The end-to-end tests drive the real compiled `ta` binary (path from `CARGO_BIN_EXE_ta`) against throwaway git repos. They're split by theme - `tests/crud.rs`, `list_search.rs`, `output_format.rs`, `deps.rs`, `merge.rs`, `undo.rs`, `compaction.rs`, `resolve.rs`, `config.rs`, `write_gate.rs`, `schema.rs`, `repair.rs`, `edit.rs` - each its own test binary starting with `mod common; use common::*;`. **`tests/action.rs`** is deliberately different and does NOT use `common`: it drives the `action/` layer through the crate's public lib API only (no binary, no `format`) - the standing guard for the frontend-agnostic claim, so if an action reaches into `cli`/`format` or the public surface stops being enough, it fails to compile. The shared harness lives in **`tests/common/mod.rs`** (a *subdirectory* module, so Cargo doesn't compile it as a standalone test binary the way a `tests/common.rs` would); add a genuinely-shared helper there (it carries `#![allow(dead_code, unused_imports)]` since each binary uses only a subset), a theme-local one in the theme file. Each test runs in its own dir under the **system** temp dir, *not* `CARGO_TARGET_TMPDIR` - that is deliberate, so `ta`'s walk-up store discovery can't climb into the repo's own `.taska` store. Merge-driver tests prepend the binary's directory to `PATH` so git's `ta git-merge ...` resolves to the binary under test. Compaction tests stay at or above the `keep_events` floor and simply generate more events than they retain. Prefer adding coverage here over ad-hoc manual scripts.

`tutorials/` holds runnable bash walkthroughs (`NN-*.sh`, driven by `lib.sh`; `run-all.sh` runs them in order) that double as UX validation and learning material. Each spins up its own throwaway repo outside the checkout. Run unattended with `TUTORIAL_NONINTERACTIVE=1`; they need `ta` on `PATH`. They are NOT part of `cargo test` - they deliberately don't `set -e` (some steps fail on purpose), so a broken step can't fail a test; instead they're validated **by hand at release time** - run `run-all.sh` and review the output (see `docs/crate_release_process.md`). So a CLI change that alters output or adds a write gate (e.g. the `--new-field` typo guard) won't trip CI; re-run the tutorials yourself after such a change.

Two gotchas when writing tests:

- **Default `--sort` is `create_time`** (oldest-first), not `id` - a test asserting row *order* must account for it or pass `--sort id`.
- When a test result contradicts how something was described, **trust the test and investigate** - it's often surfacing a real decision (e.g. an unset field's *name* reappearing as `null` was a genuine product question, not a flaky test).

## Task tracking (taska)

This repo tracks work in a local, git-native store (`.taska/`) - drive it through the `ta` CLI, never hand-edit `.taska/`. Field names, statuses, task types, and relationships are defined by `.taska/config.toml` and vary per repo, so run `ta prime` for THIS store's schema and copy-paste-ready examples, and `ta <command> --help` for a command's flags.

```bash
ta list --ready                     # actionable work: not done, all deps done
ta show <id> --full                 # one task - every field, full notes
ta create <id> <field>=<value> ...  # file new work (the status field defaults - don't set it)
ta update <id> <field>=<value> ...  # =, +=, -=  (set / append / remove)
ta dep add <id> <type>=<target>     # link a dependency
ta status                           # counts
```

Working habits:
- File a task for each distinct piece of work, before or as you start it, with `notes` rich enough for someone else to act on: the goal, intended approach/implementation details, and any open or design questions.
- For long or multi-line values, read from stdin (`<field>=@-`) or a file (`<field>=@FILE`) instead of quoting on the command line (`+=`/`-=` accept `@` too).
- Set prerequisites with `ta dep add`, and append progress to related tasks (`<field>+=...`) as things change so the trail stays current.
- Read a task's full, untruncated notes with `ta show <id> --full`.
- Commit the `.taska/` change in the same commit as the code it describes; if the store has pending changes unrelated to what you're starting, commit those first.

## Dogfooding overrides

The **Task tracking (taska)** block above is the generic workflow (auto-written by `ta init` between its markers - don't hand-edit inside them, `ta init` regenerates it). In this repo it's adjusted by:

- **Run every `ta` command as `cargo run -- <subcommand>`.** Wherever the block above says `ta`, this repo means `cargo run --` (so `ta list` -> `cargo run -- list`, `ta prime` -> `cargo run -- prime`, ...). Never invoke a `ta` on your PATH: a stale or GLIBC-mismatched installed binary runs the wrong code and can silently corrupt the log.
- **`config.toml` is plain config, not the eventlog** - edit it directly, and you must when adding a config option (see *Adding a config option: backfill the local config* above).
- **The store enforces a CLOSED schema** (`[task_types.task]`, `untyped_tasks = "deny"`): a field must be declared in `.taska/config.toml` before any task can use it, so adding a workflow field starts with a config edit. Run `cargo run -- prime` for the exact field set.
